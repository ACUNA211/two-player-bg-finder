# BGG XML API2 access, terms, rate limits, and data fields — as of September 2026

## Method note (read this first)

Direct automated fetches (`WebFetch`) to every `boardgamegeek.com` URL tried in this research — including `/wiki/page/BGG_XML_API2`, `/wiki/page/XML_API_Terms_of_Use`, `/using_the_xml_api`, individual forum threads, and even a live `/xmlapi2/thing` call — returned **HTTP 403 Forbidden** (or 401 for the raw API endpoint), including through a text-extraction proxy that showed BGG's own Cloudflare "verifying you are not a bot" interstitial page. This is itself a direct, first-hand finding relevant to sub-question 1 (see below).

Because of this, the claims below are reconstructed from **search-engine snippets of BGG's own pages** (titles, URLs, and indexed excerpts of the wiki pages and forum threads, via web search) plus a small number of secondary sources that themselves quote BGG staff verbatim with thread links. Where a claim rests only on a secondary source's paraphrase and I could not see BGG's original wording directly, it is flagged inline and again in "Uncertain / contradictory."

---

## TL;DR

- **Registration/token IS now required**, which is a change from the historically "open/keyless" XML API2. BGG began phasing in mandatory registration and OAuth-style Bearer token authorization for the XML API/API2 starting around **July 2, 2025**, announced by BGG staff (**Aldie**) in the forum thread ["XML API: Read this for uninterrupted access"](https://boardgamegeek.com/thread/3539581/xml-api-read-this-for-uninterrupted-access) — quoted (via a secondary source) as: *"We are now requiring (with a few small exceptions) registration to use the XML API."* This applies to **both commercial and non-commercial** use. The only stated exceptions are downloading your own collection, or the CSV game dump, while logged in as yourself.
- **Rate limits**: The long-standing community-documented guidance (dating to ~2014, still cited in current threads) is roughly **2 requests/second**. Limits are described in multiple forum threads as "real but not fully/officially documented," enforced with HTTP 429/503, and — per a November 2025 thread — some developers report still hitting 429s even after adding Bearer tokens. No single authoritative numeric rate limit from BGG staff could be directly retrieved and confirmed for this report; treat "~2 req/s" as a community estimate, not a confirmed BGG-published number.
- **Batching**: Community consensus (not an official BGG number I could directly verify) puts a *practical* comma-separated `id=` limit on `/thing` around **20 IDs recommended**, with reports that up to a few hundred (200–500) sometimes work but increasingly trigger backend errors/queuing; ~1000 IDs in one request is reported to reliably fail or degrade. **HTTP 202** is the documented "queued, retry the same URL later" response; retry-with-backoff is the standard community pattern (no single official numeric backoff value confirmed).
- **`/thing?id=...&stats=1` fields**: Confirmed (via a secondary source quoting real response XML, corroborated by multiple independent wrapper-library sources) that a stats=1 request does return the `suggested_numplayers` poll, `averageweight` under `<statistics><ratings>`, `minplaytime`/`maxplaytime`/`playingtime`, `thumbnail`, and `minplayers`/`maxplayers`. I could not load BGG's own wiki page directly to cite its canonical schema description, so this is corroborated-but-not-primary-sourced.

## 1. Registration / access

**This is the single most important change relative to older assumptions about the XML API2.** Historically (and as recently as this project's own briefing assumed) the XML API2 was open/keyless for reads. That is **no longer accurate as of September 2026**.

- BGG opened voluntary registration for API tokens, then moved toward mandatory enforcement, across a sequence of forum posts:
  - ["Registration and Authorization coming to the XML API"](https://boardgamegeek.com/thread/3492262/registration-and-authorization-coming-to-the-xml-a) — announcement that registration/token infrastructure was coming.
  - ["Registration to use the XML API (and obtain soon-to-be-required Tokens) is now open"](https://boardgamegeek.com/thread/3525319/registration-to-use-the-xml-api-and-obtain-soon-to) — registration opened, tokens described as "soon-to-be-required."
  - ["XML API: Read this for uninterrupted access"](https://boardgamegeek.com/thread/3539581/xml-api-read-this-for-uninterrupted-access) — posted by BGG staff **Aldie**; per a secondary source (GitHub issue, see below) this post states: *"We are now requiring (with a few small exceptions) registration to use the XML API."* Requests going forward need an `Authorization: Bearer <token>` header.
  - A GitHub issue that explicitly cites and quotes this thread: [EmilStenstrom/gamecache issue #95](https://github.com/EmilStenstrom/gamecache/issues/95), filed **July 20, 2025**, reporter "Medwynd," references BGG thread 3539581 and states the requirement covers "both commercial and non-commercial users," describes a phased rollout ("Phase 3" makes Authorization mandatory), and lists the exceptions: downloading only your own collection while logged in, or the CSV dump of all games while logged in, do not require registration. **This is a secondary source's summary/quote of BGG's own thread — I could not load the BGG thread itself to verify the exact wording, due to the 403 blocking described above.**
  - Follow-on threads confirming enforcement became real and caused breakage for existing tools: ["Heads up.... BGG now requiring authorization tokens for XML API.... could cause problems"](https://boardgamegeek.com/thread/3600185/heads-up-bgg-now-requiring-authorization-tokens-fo), ["XML API registration required" (BGG for Android forum)](https://boardgamegeek.com/thread/3540336/xml-api-registration-required), and ["\[SOLVED\] XML API authorisation failing - using bearer tokens"](https://boardgamegeek.com/thread/3602411/solved-xml-api-authorisation-failing-using-bearer).
  - A commonly cited date for when this became a hard requirement is **July 2, 2025** (surfaced in web-search synthesis of the above threads and third-party wrapper-library changelogs); a November 2025 thread (["XMLAPI rating limit avoidance recommendations with a non-commercial license"](https://boardgamegeek.com/thread/3604601/xmlapi-rating-limit-avoidance-recommendations-with)) shows developers still adapting to it and still hitting rate limiting after adding tokens ("phase 4" is referenced there as a further tightening step). **I could not independently verify the exact "July 2, 2025" date against BGG's own post — flagging as unverified-but-repeatedly-cited.**

- **Process**: Register an "application" while logged into a BGG account at `https://boardgamegeek.com/applications` (this is a logged-in-only page; I could not load its content to describe the form fields). Once BGG approves/creates the application, you obtain a Bearer token and send it as `Authorization: Bearer <token>` on XML API/API2 requests. I found **no documented turnaround-time SLA** from BGG for how long approval takes — this is not specified in any source I could retrieve; treat it as unknown, and plan for the possibility of a manual/human-reviewed step with unpredictable lead time (register early, well before the scraper needs to run).

- **Cloudflare / bot protection**: Directly confirmed by this research itself — attempts to fetch `boardgamegeek.com` wiki and thread pages via automated tooling returned HTTP 403, and a raw-content proxy showed BGG's own "This website uses a security service to protect against malicious bots... verifies you are not a bot" interstitial. This is consistent with Cloudflare (or similar) bot-protection sitting in front of at least the `boardgamegeek.com` web/wiki surface. It is unclear from this research whether the same protection gates the `xmlapi2` REST endpoints themselves for a well-behaved, token-authenticated, rate-limited scraper (as opposed to the wiki/HTML surface, which is what got blocked here) — **this needs to be tested empirically against a live token before the project commits to the weekly-scraper design.**

## 2. Terms of use

- The applicable terms live at `boardgamegeek.com/wiki/page/XML_API_Terms_of_Use`; I could not load this page directly (403). Search-indexed snippets state:
  - Use of the XML API/API2 is governed by BGG's general Terms of Service (`boardgamegeek.com/terms`) **plus** additional API-specific terms on the Terms-of-Use wiki page.
  - **Commercial use is prohibited** without a separate commercial license: *"The XML_API_Terms_of_Use prohibit use of the BGG_XML_API or the BGG_XML_API2 for commercial purposes... you must obtain a commercial license from BoardGameGeek."* A companion page exists specifically for this: ["BGG XML API Commercial Use" wiki page](https://boardgamegeek.com/wiki/page/BGG_XML_API_Commercial_Use) (content not retrievable; page's existence and title confirmed via search index). This matters for the project's stated "non-commercial" positioning — being clearly non-commercial appears to be the condition that keeps the project out of the commercial-license requirement, but the precise legal definition of "commercial" BGG uses (e.g. does ad-supported count?) is not confirmed here.
  - Search snippets referencing a secondary source (a GitHub PR titled ["Add a 'Powered by BoardGameGeek' attribution footer"](https://github.com/15Bwhitlock/game-tracker/pull/23)) suggest community practice/expectation of **attribution back to BGG** on public-facing apps using the API, but I could not confirm this is an explicit textual requirement in BGG's own Terms of Use page — **unverified against primary source.**
  - I was **not able to retrieve or verify**: specific wording on BGG logo usage rights, specific data-caching duration limits (e.g. "no more than N hours"), or explicit language about running your own independent ranking/leaderboard site built on BGG data. Searches for this specific language did not surface indexed snippets with that detail. This is a genuine gap — see "Uncertain / contradictory."
  - Sister-site mirrors (`rpggeek.com/wiki/page/XML_API_Terms_of_Use`, `videogamegeek.com/wiki/page/XML_API_Terms_of_Use`) exist and are presumed to carry equivalent Geekdo-wide terms, but these were also blocked (403) when fetched directly.

## 3. Rate limits and batching

- **Numeric rate limit**: The most repeated figure across community threads and wrapper-library documentation is **~2 requests per second**, traceable to guidance from around 2014 and still cited as the working assumption in current (2025–2026) discussions. Relevant threads:
  - ["Updated API Rate Limit Recommendation?"](https://boardgamegeek.com/thread/2388502/updated-api-rate-limit-recommendation)
  - ["Max Retry & Rate Limits for BGG XML API2"](https://boardgamegeek.com/thread/3253874/max-retry-and-rate-limits-for-bgg-xml-api2)
  - ["Rate limit exceeded on BGG api"](https://boardgamegeek.com/thread/2971538/rate-limit-exceeded-on-bgg-api)
  - ["XMLAPI rating limit avoidance recommendations with a non-commercial license"](https://boardgamegeek.com/thread/3604601/xmlapi-rating-limit-avoidance-recommendations-with) (November 2025) — describes a developer still hitting HTTP 429 after implementing Bearer-token auth, and references a further "phase 4" tightening, implying rate limiting has gotten *stricter*, not more lenient, alongside the new auth requirement.
  - I was **not able to load any of these threads directly**, so I cannot confirm exact wording, exact numbers, or whether registered/token-authenticated requests get a materially higher limit than unregistered ones. Multiple secondary summaries describe the limits as "real but undocumented officially" — i.e., even the community does not believe BGG has published an authoritative number. **Treat any specific req/sec figure (including the "~2/sec" figure above) as unconfirmed folklore, not an official BGG spec, until verified directly.**
  - Failure modes reported: HTTP 429 (Too Many Requests) and 503 (Service Unavailable) for rate/capacity issues, separate from the 202 "queued" behavior described below.

- **Batching (`/thing?id=a,b,c&stats=1`)**: No single authoritative number found. Community reports (via a secondary blog, [mixedconclusions.com "Exploring Boardgames Part One"](https://mixedconclusions.com/blog/boardgames_part_one/)) describe:
  - Batches "on the scale of around 1K games are accepted by the server, but often also cause backend errors."
  - Batches of **250–500 IDs "work well"** in that author's practical experience.
  - Other search-index snippets separately describe a commonly *recommended* (not necessarily hard-enforced) limit around **20 IDs per request**.
  - These figures are inconsistent with each other (20 vs. 250–500 vs. "up to ~1000 sometimes accepted") — this spread should be treated as a real open question, not resolved by this research. See "Uncertain / contradictory."

- **HTTP 202 behavior**: Consistently and repeatedly described across multiple sources (forum thread titles reference it directly, e.g. requests to `/thing` and `/collection` endpoints): BGG's API does not always return data synchronously. Instead, on first request it can return **HTTP 202** meaning "request accepted, queued for processing" — the caller is expected to **re-issue the identical request URL after a short delay** until a 200 with the actual payload comes back. This is described as normal, expected async behavior, most commonly encountered on `/collection` requests but also generally documented as part of the API's request lifecycle. No single official BGG-specified wait/backoff interval was found; community practice (per the mixedconclusions.com source and general wrapper-library behavior) is exponential or fixed-delay retry (commonly starting around a few seconds up to ~30 seconds, referenced in one snippet as "try again in 30 seconds").

## 4. Data fields on `/thing?id=...&stats=1`

Confirmed via a secondary source that quotes real response XML ([mixedconclusions.com](https://mixedconclusions.com/blog/boardgames_part_one/)), corroborated by search-index snippets referencing multiple independent third-party wrapper libraries (Python `boardgamegeek` package docs, Ruby `bgg-api` gem, PHP clients) that all implement parsing for the same fields — consistent independent corroboration even without a direct primary-source fetch:

- **Player-count poll**: Present as `<poll name="suggested_numplayers" title="User Suggested Number of Players" totalvotes="N">`, containing one `<results numplayers="K">` block per player count, each with three `<result value="Best|Recommended|Not Recommended" numvotes="N"/>` entries. Confirmed present in `stats=1` (and in fact in the base `/thing` response generally — the poll is not gated behind `stats=1`, only the ratings/statistics block is).
- **`averageweight`**: Confirmed present, nested inside `<statistics><ratings><averageweight value="X.XXXX"/></ratings></statistics>`, only returned when `stats=1` is passed. Also present in that same block: `usersrated`, `average`, `bayesaverage`, `stddev`, `median`, `owned`, `trading`, `wanting`, `wishing`, and (per general API knowledge, not directly re-verified here) `ranks` sub-elements for overall and per-family rank.
- **Playtime**: `<minplaytime value="N"/>`, `<maxplaytime value="N"/>`, `<playingtime value="N"/>` confirmed present as top-level `<item>` children (not gated behind `stats=1`).
- **`thumbnail`**: Confirmed present as a top-level `<thumbnail>URL</thumbnail>` element (plus a separate larger `<image>` element), not gated behind `stats=1`.
- **`minplayers`/`maxplayers`**: Confirmed present as `<minplayers value="N"/>` / `<maxplayers value="N"/>` top-level elements, not gated behind `stats=1`.

**Caveat**: I could not load BGG's own wiki page (`BGG_XML_API2`) or a live `xmlapi2/thing` response directly to visually confirm this against BGG's canonical documentation or a fresh real payload — both attempts returned 403/401. The above is corroborated by a secondary blog quoting real XML plus consistent independent wrapper-library implementations, which gives reasonably high confidence, but it is not a direct primary-source confirmation as the ticket ideally wants. **Recommend the actual scraper's first implementation step be a manual, authenticated test call against a live game ID to lock in the exact current schema before building parsing logic against it.**

## Uncertain / contradictory

- **Exact rate limit number**: No source I could reach states an official, current, BGG-published requests/second or requests/minute number. "~2 req/s" is a long-standing (2014-era) community figure still being cited, but multiple 2025 threads describe rate limiting as tightening further alongside the new token requirement, and one November 2025 thread reports 429s persisting even with a valid Bearer token. There may now be a *different* limit for token-authenticated vs. unregistered callers — this is unconfirmed either way.
- **Max IDs per `/thing` batch**: Conflicting figures found — "~20 recommended," "250–500 works well" (practitioner-reported), and "~1000 sometimes accepted but unreliable." No official BGG number found. Should be determined empirically (start conservative, e.g. 20–50, and measure).
- **Exact registration/turnaround process**: Could not confirm what the `boardgamegeek.com/applications` registration form asks for, whether approval is automatic or manually reviewed, or typical turnaround time. This is a real risk for project planning — recommend registering an application as early as possible in the project timeline, independent of when scraping work starts, in case approval is not instant.
- **Exact effective date of mandatory enforcement**: "July 2, 2025" appears in search-engine synthesis of multiple threads but I could not confirm it was BGG's own stated date rather than an inferred/aggregated date. Threads suggest a multi-phase rollout ("Phase 3," "Phase 4" referenced) rather than one hard cutover date, with tightening continuing into November 2025 at least.
- **Terms of Use specifics** (attribution wording, logo usage, caching duration limits, explicit leaderboard/ranking-site language): Not retrievable in this research. This is the weakest-covered sub-question — the project should plan to have a human log into BGG and read `boardgamegeek.com/wiki/page/XML_API_Terms_of_Use` and `boardgamegeek.com/wiki/page/BGG_XML_API_Commercial_Use` directly (a logged-in browser session may not hit the same bot-protection wall automated tooling did here), since this directly affects legal/compliance decisions for a public site.
- **Whether Cloudflare bot-protection affects the `xmlapi2` REST endpoints** (vs. just the HTML wiki/forum surface) for a properly authenticated, rate-limited script: not tested here (a raw `xmlapi2/thing` call returned 401, which is consistent with the new auth requirement rather than necessarily Cloudflare — the two are hard to distinguish from this environment). This is the single highest-priority thing to verify empirically before committing to the weekly-scraper architecture.
